# Loading interface repair — 12 September 2026

The first deferred dependency requested a Three.js r178 classic build that does
not exist (HTTP 404). Its rejected promise left the visible loading overlay at
22%, while the error was written into the removed login form.

The first dependency now uses the r178 ES module through a local adapter. Source
order remains unchanged: 64 external entries, 62 deferred, two login sources.
The loader checks download and execution failures, gives each source a timeout,
and waits for actual map tiles, country data and the canonical player surface.
Login and refresh share the same handoff. Failure keeps the partial interface
hidden and offers a clean retry.

Executing the formerly blocked stack exposed additional defects: a literal
newline escape in shared world code, an out-of-scope layout variable, missed
DOMContentLoaded initialisers, removal of a map status node still used by async
callbacks, and invalid fractional Three.js geometry segments. These are repaired.

Player card updates now avoid rewriting unchanged content. Legacy layout repair
recognises the canonical progression cards, preventing a continuous sidebar
rebuild that consumed resources and interrupted clicks. Company rendering also
skips unchanged data. No approved panel dimensions or presentation CSS changed;
the only new visible element is the retry button on loading failure.

  The test uses an isolated account and map fixture, without production account
  access or game-data mutations. It does not prove production Google Maps key
  configuration or real account authentication.

The Pages deployment depends on this regression workflow. Production account
and map verification must still be performed at the published origin.
